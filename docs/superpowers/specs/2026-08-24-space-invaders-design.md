# Space Invaders (Game #2) — Design Spec

## Context

Third milestone of the WebGL portfolio build (see `CLAUDE.md`, milestone 4:
"raise the bar: more shader work, scene management, asset loading"). Unlike
Pacman (Game #1), this game uses **real PNG textures** instead of flat-color
quads — the engine's first asset-loading feature. A small pixel-art sprite
atlas is generated by an in-repo script (no new npm dependency — Node's
built-in `zlib` handles PNG compression) and checked in as a static asset.

## Decisions

- **Sprites:** one 40×8px atlas PNG, five 8×8 cells side by side: ship,
  invader-frame-A, invader-frame-B, player-bullet, enemy-bullet. Colors are
  baked into the PNG itself (no shader tinting) — player/enemy bullets are
  two distinct sprite cells rather than one tinted sprite, keeping the
  shader simple.
- **Texture filtering:** `gl.NEAREST` (no smoothing) so the pixel art stays
  crisp when scaled up 4× for display.
- **Rendering:** one shared shader handles both textured sprites and flat
  quads (barriers) via a `uUseTexture` toggle uniform — same "one shader,
  toggle behavior" pattern as Pacman's pellet-pulse effect, extended to
  switch between sampling a texture and outputting a flat color. Position
  *and* UV are both per-vertex dynamic attributes (like Pacman's position
  buffer), computed in JS per draw call — no matrix math, consistent with
  the "no camera/projection matrices" rule carried over from prior
  milestones.
- **Engine addition:** `engine/core/Texture.js` — loads an image from a URL
  and uploads it as a WebGL texture. This is the first genuinely reusable
  (non-game-specific) engine capability added since Engine v0; it lives in
  `engine/core/` alongside `GLContext.js`/`Shader.js`, not in the game
  folder.
- **Movement:** the invader formation moves in classic discrete "marching"
  steps on a timer (not continuous per-frame motion) — this is closer to
  the original arcade feel and simpler than continuous physics. The player
  ship and bullets move continuously (per-frame, not grid-locked), unlike
  Pacman's grid movement — a deliberate contrast in movement style between
  the two games.
- **Player bullet rule:** only one player bullet may be in flight at a time
  (the original arcade's actual rule) — this also removes any need for
  bullet pooling; the player's bullet is a single nullable reference, not a
  list.
- **Barriers:** simple hit-counters (per the approved scope — "no
  pixel-destructible, solo bloquean disparos hasta que reciben N
  impactos"). Three barriers, 4 hit points each, dim visually as they take
  damage. No per-pixel destruction.
- **Difficulty scaling:** the formation's step interval shortens as
  invaders die (linear interpolation between a slow start and a fast
  finish) — the classic "fewer aliens, faster tempo" arcade feel.
- **Loss conditions:** lives reach 0 (hit by an enemy bullet 3 times), OR
  the invader formation descends far enough to reach the player's row
  (classic "invaders reached the bottom" instant loss) — both are in scope
  per the approved design.
- **Win condition:** all 25 invaders destroyed. Single wave — no escalating
  multi-wave progression, keeping scope small per the repo's house rule.
- **UI:** same HTML/CSS overlay pattern as Pacman (score/lives spans,
  overlay div with message + restart button) — reused structure, new page.

## Sprite Atlas

Generated by `scripts/generate-sprites.js` (a one-time dev tool, not game
code — exempt from the gameplay testing split below, the same way a build
script isn't unit-tested). Five 8×8 pixel-art bitmaps, packed left to right
into one 40×8 RGBA PNG, encoded by a small hand-rolled PNG writer using
`node:zlib`'s `deflateSync` (no new dependency).

Each sprite is defined as an 8-row bitmap; `1` = the sprite's solid color at
that pixel, `0` = fully transparent. Colors (RGBA):

- **Ship** — cyan `(80, 220, 255, 255)`:

  11111111

  01100110

Atlas cell `i` (0-indexed, 0=ship, 1=invaderA, 2=invaderB, 3=playerBullet,
4=enemyBullet) occupies UV rect `u0 = i * 0.2, u1 = (i+1) * 0.2, v0 = 0,
v1 = 1`.

## Components

### `engine/core/Texture.js`
`loadTexture(gl, url)` → `Promise<{ texture: WebGLTexture, width: number,
height: number }>`. Loads an `Image`, waits for it to decode, creates a
`gl.TEXTURE_2D`, uploads it via `gl.texImage2D`, sets `gl.NEAREST`
filtering and `gl.CLAMP_TO_EDGE` wrapping (no mipmaps — the atlas is tiny
and always drawn at a fixed scale). No unit test (real `Image`/`gl` calls,
browser-only) — same category as `GLContext.js`.

### `games/invaders/formation.js`
Owns the 5×5 invader grid: which cells are alive, the formation's
bounding-box position `{x, y}`, current horizontal direction, current
animation frame (`'A'`/`'B'`), and the step timer. `update(dt)` advances
the timer; when it fires, either steps horizontally (and flips the
animation frame) or — if the next horizontal step would cross the
playfield edge — descends one step and reverses direction instead. Step
interval is recomputed each tick from the count of alive invaders. Exposes
per-invader pixel positions (for rendering and collision) and a `killAt(col,
row)` mutator.

### `games/invaders/player.js`
Ship horizontal position, clamped to the playfield, moved by held
left/right (or A/D) input at a fixed speed. Owns the single-bullet-in-flight
gate: `tryShoot()` returns a new bullet only if no player bullet is
currently alive.

### `games/invaders/bullet.js`
A tiny data/update module (not a class hierarchy) for both player and enemy
bullets: `createBullet({x, y, vy, owner})`, `updateBullet(bullet, dt)`
(moves it, returns whether it's still on-screen). `owner` (`'player'` |
`'enemy'`) drives which sprite cell and collision rules apply in `main.js`.

### `games/invaders/barrier.js`
`createBarrier(x, y)` → `{x, y, width, height, hitPoints}`. `hitBarrier(barrier)`
decrements `hitPoints`, returns whether it's now destroyed
(`hitPoints <= 0`).

### `games/invaders/collision.js`
`rectsOverlap(a, b)` — pure AABB overlap test on `{x, y, width, height}`
objects. The single shared collision primitive `main.js` uses for every
bullet-vs-invader / bullet-vs-barrier / bullet-vs-player check, instead of
duplicating overlap math per pair.

### `games/invaders/renderer.js`
`createSpriteRenderer(gl, texture)` → `{ drawSprite(x, y, width, height,
cellIndex), drawQuad(x, y, width, height, color) }`. Compiles the shared
shader (position + UV attributes, `uUseTexture` toggle), builds atlas UV
rects from `cellIndex` internally. No unit test (real WebGL draw calls).

### `games/invaders/main.js`
Composition root: loads the texture (async, via `Texture.js`), then
constructs `formation`, `player`, barriers, and drives everything through
`Engine`. Owns the bullet lists (one nullable player bullet, an array of
enemy bullets capped at 2 concurrent), the enemy-fire timer, scoring,
lives, and the win/lose/restart state machine — same shape as Pacman's
`main.js`.

## Data Flow

`main.js` is the single source of truth for all mutable game state (as in
Pacman). Each frame: `update(dt)` advances `formation`, `player`, and every
active bullet; runs collision checks via `collision.js`'s `rectsOverlap`
between player-bullet/invaders, player-bullet/barriers, enemy-bullets/player,
enemy-bullets/barriers; removes dead bullets/invaders/barriers; checks
win/lose conditions. `render(gl)` is a pure read of that state, issuing one
`drawSprite`/`drawQuad` call per visible entity via `renderer.js`.

## Error Handling

Consistent with prior milestones: WebGL/shader failures fail loud
(inherited, unchanged). `Texture.js`'s image load is the one new failure
mode — if the image fails to load, the returned `Promise` rejects, and
`main.js` lets that rejection propagate (uncaught, loud) rather than
swallowing it silently, matching the project's established "fail loud, not
graceful" stance.

## Testing

Same split as Engine v0 and Pacman: pure logic gets real unit tests,
anything needing a real GPU/DOM/Image is manual-only.

- **Unit-tested:** `formation.js` (step timing, edge-detection/descend,
  direction flip, animation frame toggle, interval scaling by alive
  count), `player.js` (movement clamping, single-bullet shoot gate),
  `bullet.js` (movement, off-screen detection), `barrier.js` (hit-point
  countdown, destroyed state), `collision.js` (`rectsOverlap` — overlapping,
  touching-edge, and non-overlapping cases).
- **Manual-only:** `Texture.js`, `renderer.js`, `main.js`. Validation: run
  `vite`, open `games/invaders/`, play a full round (destroy invaders,
  take damage from enemy fire, lose a barrier, win by clearing the
  formation, lose by taking 3 hits or letting the formation reach the
  bottom, restart).
- **Not tested (dev tooling, not game code):** `scripts/generate-sprites.js`
  — a one-time asset-generation script, same reasoning as not unit-testing
  a build script.

## Out of Scope (later milestones or explicitly descoped, not this spec)

- Per-pixel-destructible barriers.
- Multiple invader waves / escalating difficulty beyond the single-wave
  formation speed-up already in scope.
- Player-bullet-vs-enemy-bullet collisions (bullets simply pass through
  each other).
- Sound effects.
- Camera/projection matrices (still not needed — static full-screen view).
